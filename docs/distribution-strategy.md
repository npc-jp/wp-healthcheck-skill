## 1. プロダクト関係性の再整理

### 役割分担（カニバリではなく階層補完）

```
[Skill: wp-healthcheck]           [Plugin: npc-wp-healthcheck]
外部・クレデンシャルなし診断        内部・管理者権限診断
─────────────────────────         ────────────────────────────────
対象: 誰でも診断可能なサイト        対象: 自分が管理するサイト
入手: GitHub/Anthropic公式         入手: GitHub（後述の判断次第）
API: 不要（curl/jq のみ）          API: Anthropic API（Claudeレポート）
情報源: 公開HTML・ヘッダー・TLS     情報源: WP管理画面API・ファイルシステム
診断精度: 外形のみ                  診断精度: ファイル改ざん・エラーログ含む
利用者: WPエンジニア・保守業者      利用者: npc既存保守クライアント向け
```

カニバリしない理由: Skillは「知らないサイトを最初に調べる道具」、プラグインは「自分が預かるサイトを毎月チェックする道具」であり、ユーザーと利用フェーズが根本的に異なる。

### ユーザージャーニー設計

```
Phase 1: 認知（Skill起点）
  Anthropicリポ / GitHub でwp-healthcheck Skillを発見
  → Claude Code で任意サイトにスキャンを走らせる
  → 「外部診断のみ / 内部診断は別ツールが必要」という限界をREADMEで認識

Phase 2: 深堀り（プラグイン訴求）
  「実際に管理しているWPサイトをもっと詳しく診断したい」
  → npc-wp-healthcheckのGitHub / n-pc.jpブログ記事に誘導
  → 自分でインストール・設定（APIキーは利用者自身のものを使う案Aなら自己解決）

Phase 3: 信頼構築（npc接点）
  プラグインの設定で詰まる / 診断結果を解釈したい
  → npc.jpのブログ記事で深堀り
  → 「WPの保守、任せませんか？」という保守契約入口（月5,000円〜）

Phase 4: 受注転換
  既存20サイト保守業務の拡大
  → Skillで診断した結果を持ってnpcに相談してくる流れ
  → 保守新規契約・単発改修受注
```

Skillは「集客ファネルの入口」、プラグインは「技術力証明の中間材」、保守契約が「出口（収益）」。

## 2. 5パターン詳細評価

### 共通前提（APIコスト試算）

Claude Sonnet 4 の現行レート（2026-04-27時点）:
- Input: $3 / MTok（= $0.000003 / トークン）
- Output: $15 / MTok（= $0.000015 / トークン）

1サイト診断あたりの粗い試算:
- Input: 5,000トークン → $0.015
- Output: 3,000トークン → $0.045
- **1診断あたり約$0.06（≒9円）**

月1回×20サイト（npc自社利用）= 約180円/月 → 自社利用は十分許容範囲。

問題は「外部公開 + APIキーをnpcが負担」した場合:
- 月100診断: 約900円/月（許容）
- 月1,000診断: 約9,000円/月（痛い）
- 月10,000診断: 約90,000円/月（**事業継続不能**）

バイラルヒット時の赤字ランナウェイが最大のリスク。

## 3. 追加パターン提案（F案・G案）

### 案F: E + C のハイブリッド（推奨の柱）

**GitHub公開版（案E）と保守クライアント向け版（案C）を並行運用する**。

- GitHub公開版: AI機能なし → 外部向けブランド実績・Anthropic公式PR用
- 保守クライアント向け版: AI機能あり（npcキー込み）→ 既存20サイトへ横展開

実装上の分岐点: `WP_ENV` 定数またはwp-config.phpの `NPC_HEALTHCHECK_API_KEY` 有無で AI Reporter の ON/OFF を切り替えるだけ。追加実装工数はほぼゼロ（定数チェック1行の追加）。

これにより:
1. GitHub公開 → 実績・ブランド露出（赤字なし）
2. 保守クライアントに同プラグイン展開 → サービス価値向上（コスト月180円以内）
3. ブログ・SNS → Skillと連動した技術コンテンツ → 問い合わせ流入

### 案G: E + A の段階的移行（司令塔の暫定推奨）

- 初版: AI機能なし（案E）で最速GitHub公開
- 3ヶ月後: 利用者自身のAPIキー設定UI追加（案A）でアップグレード

司令塔の暫定推奨と同じ方向だが、Fと比較すると「既存保守業務との接点」が薄い点が弱点。

**本戦略の推奨はFをベースに、後日Aへの対応を追加するルート。**

## 4. 推奨ルートと根拠

### 最終推奨: F案（E + C ハイブリッド）を基本に、6〜12ヶ月後にA拡張

1. **赤字リスクがゼロ**。APIコストは既存保守業務のコストとして月180円で収まる
2. **追加実装工数が最小**。既存v0.5.1の `NPC_HEALTHCHECK_API_KEY` 有無チェックを活用すれば分岐はほぼタダ
3. **既存20サイト保守業務に直接乗る**。「診断レポート付き保守」の実績がたまれば保守単価の値上げ交渉材料になる

## 6. 既存n-pc.jp導入版との整合

### 判断: 統合（分岐なし）+ 環境変数での機能ON/OFF

**分岐（別ブランチ・別ファイル）はしない**。コードは同一、`wp-config.php` の定数有無で挙動が変わる設計を採用する。

実装イメージ:
```php
// includes/class-ai-reporter.php
public function is_available(): bool {
    return defined('NPC_HEALTHCHECK_API_KEY') && NPC_HEALTHCHECK_API_KEY !== '';
}
```

```php
// 管理画面ビュー側
if ( $reporter->is_available() ) {
    // AIレポートボタン・自動診断設定を表示
} else {
    echo '<p>AI Reporterを使用するにはwp-config.phpにNPC_HEALTHCHECK_API_KEYを定義してください。</p>';
}
```

これにより:
- **GitHub公開版**: インストールしたままではAI機能なし → 赤字ゼロ
- **n-pc.jp（自社利用）**: `NPC_HEALTHCHECK_API_KEY` 定義済み → 現行通り動作
- **保守クライアント版**: npcが展開時にwp-config.phpへ定数追記 → AI機能有効

後方互換の保証: v0.5.1の `NPC_HEALTHCHECK_API_KEY` 仕組みはすでに存在するため、追加実装は「未定義時の非表示処理」の追加のみ。

### Gitブランチ戦略

```
main ブランチ: 外部公開版（= GitHub公開と同じ内容）
自社運用: main を各サイトにデプロイ、wp-config.php でAPIキーを注入
```

`npc-private` 等の非公開ブランチは作らない（管理コストが増えるため）。

## 8. 判断待ちポイント（Q1〜Q8）

以下について Azu に最終判断を仰ぐ:

**Q1. プラグインの公開範囲**
GitHub公開するか、保守クライアント限定配布のみにするか。
- GitHub公開すれば実績・ブランド露出に繋がるが、インストール・サポート問い合わせが来る可能性がある
- 保守限定にすれば管理が楽だが外部への訴求力はない
→ 推奨: GitHub公開（AI機能なし版）

**Q2. WordPress.org への提出**
プラグインをWordPress公式プラグインディレクトリへ提出するか。
